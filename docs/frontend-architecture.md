# Архитектура фронтенда

Фронтенд — Nuxt 4 (SPA, `ssr: false`) + PWA. Данные живут на устройстве в IndexedDB (Dexie), сервер — цель синхронизации.
Этот документ описывает, **как устроен код сейчас** и по каким правилам его менять. Почему некоторые вещи сделаны именно так —
в [ADR](./adr/README.md).

## Принципы

1. **Устройство — первичное хранилище.** Приложение работает без сети; до регистрации оно вообще не обращается к серверу.
2. **Запись в БД — только через «писателей»** (`useEventWriter`, `useEntityWriter`). Страницы и компоненты не вызывают
   `db.*.add/update/put` и не вызывают `enqueue` напрямую.
3. **Состояние семьи выводится из событий** и не правится руками ([ADR 0001](./adr/0001-colony-state-derived-from-events.md)).
4. **Что зависит от типа события — описано таблицей `Record<EventType, …>`**, а не цепочкой `if/switch`
   ([ADR 0003](./adr/0003-event-types-as-typed-tables.md)).
5. **Чистая логика — в `utils/`** и покрыта тестами; компоненты остаются склейкой.

## Карта папок (`frontend/app`)

| Папка                      | Что внутри                                                                                                  | Правило                                                                                                 |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `pages/`                   | маршруты                                                                                                    | загрузка данных (`useLiveQuery`) → компоненты → писатель. Бизнес-логики и прямых запросов на запись нет |
| `components/ui/`           | кирпичики интерфейса (`BaseButton`, `FormShell`, `SheetItem`, `PageSection`, …)                             | **не знают про пасеку**: никаких семей, ульев и событий                                                 |
| `components/layout/`       | каркас приложения (`AppPage`, `AppTopbar`, `BottomBar`, …)                                                  |                                                                                                         |
| `components/<домен>/`      | `colony/`, `hive/`, `queen/`, `event/`, `apiary/`, `auth/`, `analytics/`                                    | компонент нужен одному домену — кладём в его папку                                                      |
| `components/event/fields/` | поля формы события, по компоненту на тип (или группу типов)                                                 | получают форму через `defineModel`                                                                      |
| `composables/`             | `useEventWriter`, `useEntityWriter`, `useSync`, `useAuth`, `useFormSubmit`, `useLiveQuery`, `useEventHints` | всё, что требует Vue-контекста, Dexie или сети                                                          |
| `utils/`                   | чистые функции без Vue                                                                                      | см. «Утилиты и автоимпорт»                                                                              |
| `utils/analytics/`         | расчёты вкладок аналитики                                                                                   | вызываются явным импортом                                                                               |
| `shared/db/`               | схема Dexie и типы локальных сущностей                                                                      | единственное место, где объявлены таблицы                                                               |
| `shared/api/schema.d.ts`   | типы API, **генерируются** (`bun run gen:api`)                                                              | руками не править                                                                                       |
| `plugins/`                 | `api` (клиент `openapi-fetch`), `sync.client` (синк при старте/возвращении онлайн), `vue-konva`             |                                                                                                         |
| `assets/scss/`             | переменные и общие стили                                                                                    |                                                                                                         |

Имена компонентов не зависят от вложенности (`components: [{ path: "~/components", pathPrefix: false }]`):
файл `components/ui/BaseButton.vue` — это `<BaseButton>`.

## Правила

### Запись данных

```
страница: валидация → run(() => writer.метод(...)) → returnTo(...)
```

- `useEventWriter`: `saveEvent`, `saveQueenChange`, `deleteEvent`. Одна транзакция: событие + пересчёт состояния семьи
  (`deriveColonyState` → `applyColonyState`), затем `enqueue` в очередь синка.
- `useEntityWriter`: улей, матка, семья (`createHive`, `updateHive`, `moveHive`, `createColony`, `assignColonyToHive`, …).
  Составные операции (семья + улей + переезд + матка) — одна транзакция.
- Ошибки БД пробрасываются наружу; текст ошибки для пользователя ставит `useFormSubmit().run`.
- Новая операция записи = новый метод писателя, а не `db.*` в странице.

### Формы

- Оболочка — `FormShell` (отступы, блок ошибки, кнопка) + `useFormSubmit` (`submitting`, `error`, `run`).
  Содержимое после кнопки (удаление) — слот `footer`.
- Состояние — один объект формы на странице (`ref<HiveForm>`, `reactive(EventForm)`).
  Преобразование «строки формы ↔ сущность» только через `utils/entityForms.ts` и `utils/eventPayload.ts`
  (обрезка пробелов, `parseInt`, «пусто → не попадает в сущность»).
- Группа полей — компонент с `defineModel<…>`, который мутирует поля формы по месту
  (`HiveFormFields`, `QueenFormFields`, `components/event/fields/*`). Проп `edit` включает режим правки.
- Валидация события — `isEventFormValid` и таблица `FORM_RULES` в `eventPayload.ts`.

### Чтение данных

- `useLiveQuery(querier, initial)` подписывается на Dexie и пересобирает данные при любых изменениях.
- Всегда фильтруем `deletedAt`: удаление мягкое.
- Ссылка семьи на удалённый улей/матку считается **пустой** (`needsHive` в `utils/colonyRefs.ts`; `ADR 0001`).

### События

Всё, что зависит от `event.type`, лежит в таблице с типом `Record<EventType, …>`: пропущенный тип не соберётся.
Неизвестный тип от более нового сервера не должен ломать UI (запасной вариант в `getEventSummary`/`getEventFields`).

**Как добавить тип события:**

1. Бэкенд: схема payload и `eventInput` (`backend/src/features/events/schema.ts`), вывод состояния, если оно меняется.
2. `shared/db/index.ts` — `EventType`.
3. `utils/eventPayload.ts` — `PAYLOAD_FIELDS` (и `FORM_RULES`, если есть обязательные поля, `APIARY_SCOPED_TYPES`, если без семьи).
4. `utils/eventLabels.ts` — `EVENT_FORM_TITLE`.
5. `utils/eventSummary.ts` и `utils/eventDetails.ts` — записи в `DESCRIBE` (TypeScript потребует их сам).
6. `utils/colonyState.ts` — `deriveColonyState` (если влияет на семью) и `STATUS_BY_EVENT_TYPE` (если меняет статус).
7. `components/event/fields/` — поля; ветка в `pages/events/new.vue`; строка в `components/event/NewEventSheet.vue`.
8. `EDITABLE_EVENT_TYPES` в `eventDetails.ts`, если событие можно править.

### Стили

- **Scoped-стили родителя не действуют внутри дочерних компонентов.** Класс, которым пользуется вынесенный
  компонент, объявляется в нём самом.
- Повторяющиеся блоки — компонент в `components/ui/` (`SheetItem`, `PageSection`, `FabButton`, `NotFoundState`).
- Общие стили вкладок аналитики — `assets/scss/analytics.scss`, все правила под `.analytics`, чтобы не пересекаться
  с одноимёнными классами других страниц.
- Цвета и отступы — только через CSS-переменные (`--color-*`, `--space-*`).

### Движение

Значения (длительности, сдвиг, кривая) — токены в `assets/scss/variables.scss`; в компонентах числа не дублируем.
Анимируем только `transform` и `opacity`.

- **Страницы:** View Transitions, M3 «shared axis X» (стили в `app.scss`). Направление выставляет
  `plugins/nav-direction.client.ts`; возврат после сохранения или удаления делайте через `returnTo`.
- **Вкладки и данные на месте:** `<Transition>` с именами `tab-forward`/`tab-back` и `swap`; строки списков —
  `<TransitionGroup name="list">`; раскрывающиеся блоки — `ui/Collapse.vue`; подтверждения — `useToast()`.
- **Не ставьте `transform` на корень страницы или её предков:** он ломает `position: fixed` внутри (плавающая «+»,
  схема ульев). Для страниц допустим только `opacity`.
- `Collapse` ставьте рядом с его кнопкой в одном контейнере: иначе у родителя с `gap` остаётся пустой промежуток.

### Утилиты и автоимпорт

- Файлы **верхнего уровня** `utils/` и `composables/` подключаются Nuxt автоматически. Вложенные (`utils/analytics/`)
  и типы — только явным импортом.
- Утилиты, которые тестируются в `bun test`, **не должны полагаться на автоимпорт** (его в тестах нет): импорты явные,
  относительные (`./constants`).
- Имена функций в `utils/` глобальны: давайте им говорящие имена (`payloadNum`, а не `num`).
- После добавления файла в `utils/` или `composables/` выполните `bun run postinstall` (`nuxt prepare`): иначе IDE
  и `eslint` некоторое время не видят новый автоимпорт.

### Тесты

- `bun test test/` — только чистые функции: разбор форм, расчёты аналитики, описания событий, геометрия схемы, синк-помощники.
- Эмуляцию IndexedDB (`fake-indexeddb`) сознательно **не** подключаем: записи тонкие, чистые части выделены и проверяются.
- Что завязано на Dexie, сеть или canvas, проверяется вручную.
- При рефакторинге сначала фиксируем текущее поведение тестами, потом меняем код.

### Перед коммитом

```bash
bun run lint        # eslint
bun run typecheck   # nuxt typecheck (vue-tsc)
bun run test        # bun test test/
bun run build       # nuxt build
```

## Что сознательно не делаем

- **Единый реестр свойств типа события** (заголовок, иконка, поля, редактируемость в одной записи). Сейчас это таблицы
  в 4–5 файлах; реестр станет оправданным, если добавление типов станет частым.
- **Общая форма «семья + улей»** вместо отдельных `colonies/new` и `hives/new`: у них разный интерфейс (группы полей,
  «заселить»), слияние изменило бы поведение.
- **Список семей отдельной страницей.** Семья воспринимается в связке с ульем; страницы `/colonies` нет
  (семья доступна через улей, а без улья — через «Привязать семью» на пустом улье).
- **Локальное «исправление» состояния семьи.** Оно пересчитывается из событий и всё равно перетрётся при синке.

## Инструменты анализа

Конфиг `fallow` — `frontend/.fallowrc.json` (исключает сгенерированную схему API, объявляет тесты и SCSS точками входа).
Используется для поиска дублей, сложных функций и мёртвого кода; метрики — ориентир, а не требование.
